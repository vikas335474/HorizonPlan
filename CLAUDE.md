# HorizonPlan

B2B2C retirement planning platform for Indian MFDs/IFAs and SEBI-RIA firms. Full context lives in `/docs/` — read the relevant file before starting work on that area, don't assume this file alone is enough.

## Stack
PHP (no framework) + PDO + MySQL, hosted on Hostinger Premium. React SPA (Tailwind, shadcn/ui), pre-compiled — Hostinger serves static files, it does not run a Node build step, so the frontend must be built (`npm run build`) before every deploy. A `.github/workflows/deploy.yml` pipeline now automates this by publishing the compiled output to a `deploy` branch — see "Deploy" below and `DEPLOY.md`. A parallel `deploy-staging.yml` pipeline (push to `develop` → `deploy-staging` branch) publishes to a fully separate staging subdomain/database, for admin/dev/testing work that shouldn't touch production or real trial-signup data — see `DEPLOY.md`'s "Staging environment setup".

## Non-negotiable rules (always apply, every session)
1. **Tenant isolation:** every query on tenant-scoped data goes through `api/lib/TenantScopedDb.php`. Never write a raw `WHERE tenant_id = :tenant_id` inline in an endpoint file — if the helper doesn't exist yet, build it first (see `docs/02`, Section 3.1).
2. **`advisory_mode` on tenants is Super Admin-only**, enforced server-side, never a self-serve toggle. See `docs/02` Section 3.6.
3. **Distribution-mode disclosure copy** renders on every client-facing plan view, and directly adjacent to the withdrawal-rate slider and projection chart specifically.
4. Every mutation to `base_plans` / `sub_scenarios` writes to `change_log`.
5. No credentials in the repo. `db_config.php` stays out of git.
6. Don't build anything from `docs/04`'s "explicitly out of scope" lists without checking the phase validation gate first.

**Bug fix, same session — every modal lost input focus after one character.** Reported directly by the user ("I need to click somewhere else to type second letter... Add client or Fork template popups"). Root cause, found in `components/Modal.jsx`: a single `useEffect` both wired the Escape-key listener and called `panelRef.current.focus()`, keyed on `[open, onClose]`. Nearly every call site passes `onClose` as a fresh inline arrow function, so it's a new reference on every re-render; typing a character updates the parent's state, re-rendering the modal, handing the effect a new `onClose` reference, rerunning it, and calling `.focus()` again — yanking focus from the input straight back to the dialog container. Fixed by reading `onClose` through a ref kept current every render, so the effect's dependency array is just `[open]` — it now only fires on actual open/close, not on every keystroke. Verified by reproducing the bug first (temporarily reverted the fix, ran a live Playwright test typing into the Add Client email field, confirmed only the first character landed — matching the report exactly), then confirming the fix resolves it. One file fixes every modal in the app at once.

## Security status
Phase 8 audit gaps now resolved — MFA, CSRF double-submit tokens, and **mandatory MFA enrollment** are all implemented. No pre-launch security gap remains open from this audit trail; per-field validation on `goals_update.php`/`goals_create.php` (the one item flagged as out of scope for the original three audit sessions) is now closed too — see the write-up above.

**Mandatory MFA enrollment (closes the last Phase 8 gap).** Decision: enforce server-side, no grace period — every session, for every role (advisor/client/super_admin), is blocked from every endpoint except `mfa_enroll.php`/`session.php`/`logout.php` until `users.mfa_secret` is set. Considered the alternative (an admin-configurable grace period before a hard block) and rejected it as unnecessary complexity for this deployment model: every account here is admin-provisioned (`docs/04`'s "Tenant onboarding (admin-created, not self-serve signup)"), so there's no signup funnel to protect from friction — an advisor/client's very first login can require a two-minute TOTP setup without costing a conversion the way it would on a self-serve product. `login.php` still issues a full session on password alone regardless of enrollment (unchanged — restructuring the pending-token dance to withhold the session itself would have meant enrollment endpoints could no longer authenticate the user trying to enroll); the actual gate lives one layer up, in `verifyAccess()`/`verifyAccessAny()` (`api/lib/security_gatekeeper.php`), which now call a new `requireMfaEnrollment()` by default (`$requireMfaEnrolled = true` param, opt-out via `false`) and 403 with `mfa_enrollment_required: true` for any unenrolled session. Every one of the ~40 existing endpoint call sites picked this up automatically with zero code changes, since the gate lives in the shared helper both `verifyAccess()` call conventions already route through — the single explicit exemption is `mfa_enroll.php` itself (`verifyAccessAny(..., false)`), which must stay reachable precisely so an unenrolled user has a way to enroll. The underlying check (`userHasMfaEnrolled()`) is a separate, side-effect-free function specifically so it's unit-testable against a real DB without needing to exercise the 403-and-exit path over HTTP. Frontend: `ProtectedRoute.jsx` now redirects any authenticated-but-unenrolled session to `/settings` (carrying `mfaRequired` + the original destination in router state) instead of the no-op it was before — this is a UX convenience on top of the server-side block, not the actual enforcement. Fixed a real bug found while building the Playwright walkthrough for this: `Settings.jsx`'s `MfaSection` showed the post-enrollment "Continue" button only in a transient local `phase === 'done'` state that got superseded by the `enrolled` prop flipping true (via `refreshSession()`) before a human could realistically see or click it — a user completing forced enrollment could get stranded on the "Enabled" card with no visible way to proceed. Fixed by moving the Continue button into the `enrolled` early-return branch itself and dropping the now-redundant transient phase. Verified against a real MySQL instance, a real HTTP request/response cycle, and a real browser: `tests/test_mfa_enforcement_db.php` covers `userHasMfaEnrolled()` for all three roles including the NULL-vs-empty-string and nonexistent-user (fail-closed) edge cases; a live `php -S` + curl cookie-jar session confirmed an unenrolled advisor's session works for `session.php`/`mfa_enroll.php`/`mfa_enroll_confirm.php` and 403s with `mfa_enrollment_required` on `goals_list.php`/`password_update.php`, that enrollment completion immediately lifts the block (subsequent `goals_list.php` call reaches its own normal business-logic response instead of the gate), and that an already-enrolled user's existing login→OTP→session flow is completely unaffected; a Playwright run against the real dev server (`php -S` + `vite dev`) walked an unenrolled advisor through login → redirect to `/settings` with the banner → the gate holding even against a direct URL navigation to a deep link (`/goals`) → enrolling → "Continue" correctly returning to that original deep link → the header's amber nudge dot clearing, with zero real JS exceptions.

### Audit findings, file-by-file

**MFA** — **Implemented** (RFC 6238 TOTP, no external dependency — `api/lib/Totp.php` is pure PHP). Login forks on `users.mfa_secret`: enrolled users get a 202 + short-lived `hp_mfa_pending` cookie, then submit OTP to `mfa_verify.php` for a full session. Enrollment is a two-step flow (`mfa_enroll.php` → `mfa_enroll_confirm.php`) available to any authenticated user. Pending tokens live in `mfa_pending` (migration 008), are single-use, expire in 10 min, carry the TOTP secret server-side in `payload` so it never lives in JS. **Enrollment is now mandatory** — see "Mandatory MFA enrollment" above for the full writeup; the mechanism here (TOTP generation/verification, the enroll/confirm handshake) is unchanged, only the enforcement around it is new. **A verified Google login is now a second, independent way to satisfy the same mandatory requirement** — see "Google Sign-In" above; `userHasMfaEnrolled()` checks `mfa_secret OR google_sub`, and `login.php` blocks password-only login for an account that has linked Google but never set up TOTP, so linking Google can never silently downgrade the password path to single-factor.

**CSRF protection** — **Implemented** (double-submit cookie pattern). `issueSession()` and `session.php` now set a non-httpOnly `hp_csrf` cookie alongside the httpOnly session cookie. `verifyAccess()` and `verifyAccessAny()` call `verifyCsrfToken()` on every non-GET request, checking `hash_equals($cookie, $header)` where the header is `X-CSRF-Token` sent by the frontend's fetch wrapper (`api.js`, reads the cookie and attaches it). `destroySession()` clears both cookies. **Password reset (self-service, added post-Phase-8)** — Until this addition, the only account-recovery path was the CLI-only `tools/set_password.php`/`tools/bootstrap_admin.php` (SSH access required) — unworkable for real advisor/client tenants who can't SSH into the server. `password_reset_request.php` / `password_reset_confirm.php` add an email-link flow: `password_resets` (migration 009) stores only a SHA-256 hash of the token (never the raw value — a stricter property than `mfa_pending`'s stored-raw-token, since a leaked reset token alone is a full account takeover, not a second factor); tokens are single-use (`used_at`) and expire in 30 minutes; the request endpoint's response is byte-identical whether or not the email exists (anti-enumeration) and is rate-limited to one live token per user per 2 minutes; redeeming a token invalidates every other outstanding token for that user and clears all of that user's `active_sessions`. ## Deploy
**Automated (preferred):** `.github/workflows/deploy.yml` builds the React app on every push to `main` (touching `frontend/`, `api/`, or the workflow) and publishes a `public_html`-shaped tree — compiled `dist/` at the root plus `api/` under `/api` — to a dedicated **`deploy` branch**, building on top of that branch's history (never force-pushed) so Hostinger's `git pull` always fast-forwards. Hostinger's native Git deployment (hPanel → Advanced → GIT, branch `deploy`, directory `public_html`) pulls it automatically. `api/db_config.php` is stripped in CI and lives only on the server, so pulls never touch it. **Full setup + gotchas in `DEPLOY.md`.** Note: the workflow only fires from `main`, so it activates after this branch is merged, not on the feature branch itself.

**Manual fallback:** build locally (`cd frontend && npm run build`), then upload the `dist/` output into `public_html` via Hostinger's File Manager alongside `public_html/api`. Watch two things this replaces: `.htaccess` is a hidden dotfile inside `dist/` that file managers drop, and every `dist/` file (including `assets/`) must land at the `public_html` root together or the absolute `/assets/…` paths 404.

SQL migrations in `/sql` are **not** run automatically under either path — run new migrations manually via hPanel's database tool after each deploy that includes one.
