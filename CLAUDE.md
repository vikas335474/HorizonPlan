# HorizonPlan

B2B2C retirement planning platform for Indian MFDs/IFAs and SEBI-RIA firms. Full context lives in `/docs/` — read the relevant file before starting work on that area, don't assume this file alone is enough.

## Stack
PHP (no framework) + PDO + MySQL, hosted on Hostinger Premium. React SPA (Tailwind, shadcn/ui), pre-compiled — Hostinger serves static files, it does not run a Node build step, so the frontend must be built (`npm run build`) before every deploy. A `.github/workflows/deploy.yml` pipeline now automates this by publishing the compiled output to a `deploy` branch — see "Deploy" below and `DEPLOY.md`. A parallel `deploy-staging.yml` pipeline (push to `develop` → `deploy-staging` branch) publishes to a fully separate staging subdomain/database, for admin/dev/testing work that shouldn't touch production or real trial-signup data — see `DEPLOY.md`'s "Staging environment setup".

## Non-negotiable rules (always apply, every session)
1. **Tenant isolation:** every query on tenant-scoped data goes through `api/lib/TenantScopedDb.php`. Never write a raw `WHERE tenant_id = :tenant_id` inline in an endpoint file — if the helper doesn't exist yet, build it first (see `docs/02`, Section 3.1). (A few read endpoints that need a `JOIN` the helper can't express — `clients_list.php`, `change_log_list.php`, `goals_review_queue.php` — drop to a raw *tenant-scoped* query; that's the one documented exception pattern, always still tenant-filtered.)
2. **`advisory_mode` on tenants is Super Admin-only**, enforced server-side, never a self-serve toggle (a `firm_admin` can self-serve branding but NOT `advisory_mode`). See `docs/02` Section 3.6.
3. **Distribution-mode disclosure copy** renders on every client-facing plan view, and directly adjacent to the withdrawal-rate slider and projection chart specifically.
4. Every mutation to `base_plans` / `sub_scenarios` writes to `change_log`.
5. No credentials in the repo. `db_config.php` **is** in git (a secret-free loader — see "Deploy" below), but the real credentials it points to never are.
6. Don't build anything from `docs/04`'s "explicitly out of scope" lists without checking the phase validation gate first.

## Working conventions (how sessions here operate)
- **Decide-then-build:** for anything with a real schema or product decision, confirm the open choices with the user (via `AskUserQuestion`) *before* writing a migration. `docs/09`/`docs/10` prompts are written this way; follow it.
- **Verify for real:** this codebase's bar is a real MySQL instance + a real HTTP request/response cycle + (for UI) a real Playwright browser run — not static review alone. Install `mariadb-server`, apply all `/sql` migrations, run `tests/run_all.sh`, and drive the actual dev servers (`php -S -t api` + `vite dev`). Nearly every entry in the history log was caught or confirmed this way.
- **Guardrail-style caution:** ship the *mechanism*, not an opinion, where the firm should supply content (risk questionnaire, strategy templates); default new firm-wide toggles OFF; never silently degrade an existing tenant on a migration (explicit backfill).
- **Known landmine:** several `tests/*_db.php` files were fixed to wrap their fixtures in transactions (docs/09 Session 2), but there is still no hard guard stopping `tests/run_all.sh` from running against a database that holds real/demo data. Point tests at a disposable DB.

## Current state — what's built (capability index)
Phase 1 (MVP) and the documented Phase 2 core are built, plus a long series of hardening/demo/UX sessions. **This is a *planning-and-conversation* tool, not a transaction back-office** — see `docs/10` for the honest competitive framing (no order routing, KYC, or commission reconciliation, by design). For the full story behind any item below, see `docs/CHANGELOG_SESSION_HISTORY.md`.

**Core planning engine** (`api/lib/PlanMath.php`, pure arithmetic, no DB) — decumulation projection, accumulation (SIP + step-up) → decumulation as one lifecycle, corpus composition (liquid/locked two-bucket, spend-liquid-first), sequence-of-returns (steady vs. adverse), historical sequence replay (real market years, `market_history`, unverified-data flagged), and the blended 0–100 Retirement Readiness Score. `goals_projection.php` surfaces all of it; series are shared via `decumulationSeriesForGoal()`/`readinessScoreForGoal()`. The baseline steady-vs-adverse chart renders on **every** projectable goal's detail page (it used to appear only inside a sub-scenario, so a decumulation-only goal showed no chart at all). Target-based goals (education/home/other) — which carry no rate to project from — get `targetGoalFunding()` instead: the target inflated to its target date plus what today's corpus covers of it, **assuming no growth**, since those goal types have no return assumption and the app won't invent one.

**Plans & scenarios** — multi-goal `base_plans` (retirement/education/home/other) + `sub_scenarios` what-ifs through the Global Inheritance Engine cascade (single shared `is_overridden` flag). Per-field validation (`GoalFieldValidation.php`) shared by create/update. Full edit UI on `GoalDetail.jsx` (plan params, accumulation, corpus composition), gated so a client sees no advisor-only edit affordance.

**Strategy templates** — global + firm templates/customizations, approval-gated (`draft`/`approved`), apply-to-goal writes the return assumption + cascades + logs a `used_in_plan` audit row. `super_admin` approves global; `sr_advisor`/`firm_admin` approve firm-owned.

**Risk profiler** — per-tenant question set + scoring rubric the *firm* supplies (never HorizonPlan-authored), approval-gated; captured profiles surface a suggested return only when the set is approved (read-time gate). Authoring UI + client-facing questionnaire.

**Goal progress over time** (docs/10 P1-1) — `goal_snapshots` + `client_net_worth_snapshots` (migration 032) record what a goal's corpus **actually** was and what the plan **expected** on each date, plus the client's net worth as a deliberately **separate** series (docs/02 §4.1 — the portfolio is not a pool a goal draws from). Captured by a **monthly cron** (`tools/progress_snapshot.php`, see `DEPLOY.md`) and by an advisor's "Record now" (`progress_capture.php`); **idempotent per day**, and never backfilled — history starts when tracking does. `expected_value` is stored at capture time, not recomputed, so a later plan edit can't rewrite the past. Drift is classified by `PlanMath::progressStatus()` with a deliberate **±5% dead zone**; target-based goals (no return assumption) track **funding coverage** instead of drift. Surfaced as a chart on the goal page, a "Behind plan" badge on the roster, and a section in the client report.

**Client portfolio** — `client_portfolio_items` ledger (assets/liabilities, liquid/locked, net worth computed on read), grouped into Market-linked / Bank & cash / Retirement & long-lock / Property / Other so the full instrument set (mutual funds, stocks, **bonds, REITs/InvITs** — new — gold, savings, FD, **cash** — new — PPF, EPF, NPS, real estate, plus liabilities) is actually discoverable, not a flat dropdown. A **daily MF NAV price-sync cron** (`mf_nav_cache`, `tools/mf_nav_sync.php`, migration 027) refreshes tracked holdings from cached NAVs (manual "Refresh prices" uses the cache, no live call). *Not* a live RTA folio feed.

**CAS/MFCentral CSV import — reconcile by holding** (docs/12 Prompt D-1, sql/038) — rewritten from the original behavior, which unconditionally *inserted* every row, silently duplicating a client's whole mutual fund book on a second upload. Now a two-step preview → confirm flow: `client_portfolio_reconcile_preview.php` computes a diff (`api/lib/PortfolioReconcile.php`, pure, no DB) against the client's own prior CAS-sourced holdings, matching primarily on **folio number** (the one field that survives a fund's display name changing between statements) and falling back to a normalised-name match flagged lower-confidence in the UI; `client_portfolio_import.php` **recomputes the same diff server-side** (never trusts a client-submitted diff) and applies it in one transaction — update matched holdings' values, insert new ones, and delete only ids the user explicitly confirmed **and** the recomputed diff independently still flags as missing (`confirmedPortfolioRemovalIds()` — a client can never smuggle an unflagged id, e.g. a hand-entered holding's, into a deletion request; verified live over HTTP, not just in tests). Reconciliation is scoped to `source='cas_import'` rows only — a new `client_portfolio_items.source` column (`'manual'|'cas_import'`, default `manual`, no separate backfill needed) means **a hand-entered holding is never matched, updated, or deleted by an import, even on a folio/name collision** (proven with a live HTTP call: `remove_ids` intentionally included a manual row's id, and the server dropped it while still removing the legitimately-flagged one). `folio_number` (nullable) is the new match-key column, stored separately from the display `description` rather than baked into it as before. The upload flow also gained an inline, per-source (CAMS/KFintech/MFCentral) step-by-step "how do I actually get a CAS" guide, since the previous copy assumed the user already knew.

**Per-instrument tax context — facts only** (docs/12 Prompt D-2, sql/039) — every asset row on `ClientPortfolioCard` gets a collapsed-by-default "Tax context" panel: the sourced capital-gains/holding-period treatment that would apply if sold today, and an **illustrative unrealised gain** when a purchase price was recorded. Deliberately never a filing figure or a "sell now"/"harvest now" prompt — this app has no transaction ledger, so it cannot know how much LTCG exemption is already used this year, only the gain on what's still held; docs/12's own "headroom" wording was corrected to this narrower, honest claim on the record. `tax_reference` (14 rows: mutual_fund ×3 fund types, stocks, bonds, reits, gold, real_estate, savings, fd, cash, ppf, epf, nps — same table+cron shape as `reference_costs`, `tools/tax_reference_sync.php`) seeds every row `is_verified=false`, since Indian capital-gains rules changed substantially in the 2023/2024 budgets and move again every budget after. A new `client_portfolio_items.fund_type` (`equity`\|`debt`\|`hybrid`, nullable) exists because a generic "mutual fund" category cannot get one correct tax note — the two regimes are taxed completely differently, and an unset `fund_type` shows all three regimes side by side rather than guessing. New nullable `acquisition_value`/`acquisition_date` (independent of each other, asset-only, no backfill) unlock the gain/holding-period facts; absent, the panel still shows the treatment note and says "add a purchase price to see an illustrative gain." Surfaced identically for both advisor and self-serve individual sessions.

**Goal-met state** (docs/12 Prompt D-3) — `PlanMath::targetGoalFunding()` and `PlanMath::retirementTarget()` each gained an explicit `is_met` boolean (reading the *unclamped* coverage ratio, so a goal that only just crosses the line still reads met even where the display figure clamps at 100%). Investigating this prompt found its own "moves as prices move" premise was already half-true: both functions already recompute against the *current date* on every call — only the goal's own recorded corpus (`initial_net_worth`) is static, deliberately decoupled from the NAV-tracked portfolio (docs/02 §4.1); the real gap was a missing name for a state the math already implied, not new math. No hysteresis/dead-zone — a documented deferral, since a static corpus can't flicker day to day; worth building only once/if the (still-deferred) live portfolio↔goal link ships. Surfaced on `GoalCard.jsx` (roster), `GoalDetail.jsx`/`RetirementTargetCard.jsx` (detail page), and a new firm-wide **"N goals met target"** dashboard card (`clients_list.php`'s `stats.goals_met_count`) — scoped to target-based goals only (cheap, drift-proof against the goal's own page), mirroring the existing retirement-only scope of `min_readiness_score` in the same file; a retirement goal's `is_met` still renders correctly on its own detail page, just isn't folded into the firm-wide count.

**Alerts / rules engine** (docs/12 Prompt D-4) — the unifying surface both dashboards read through. A pure `AlertsEngine.php` computes five typed, factual triggers (`{type, severity, subject, factual_message, deep_link}`, `severity` ∈ `positive`\|`attention`, the app's existing teal/amber framing): `goal_met` (D-3's `is_met`), `goal_drift` (existing `progressStatus()`'s ±5% dead zone), `price_stale` (the NAV cron's `nav_fetched_at` freshness signal, or "price pending" for a never-priced row), `review_due` (existing `plan_review_schedules` via `PlanReviewMailer.php`'s own cadence mapping — never a second definition of "due"), and `foundations_gap` (any non-passing `FinancialFoundations` check). A sixth candidate — LTCG exemption headroom — was dropped: D-2 never built a headroom figure (no transaction ledger), so there's no honest fact behind it. Every message is asserted, in tests, to never contain an instruction word ("sell", "should", etc). `AlertsInputs.php` assembles one client's bundle — a retirement goal's `is_met` mirrors `goals_projection.php`'s own lifecycle computation so an alert can never disagree with the goal's own page; the foundations block reads through a new extraction, `foundationsSummaryForClient()` (`FoundationsInputs.php`, pulled out of `foundations_read.php`'s previously-inline logic so the alerts engine and a client's own foundations page can't drift apart — `foundations_read.php` is now a thin wrapper). `alerts_read.php` is the per-client endpoint (advisor-or-client, same forced-to-own-id rule as `foundations_read.php`); `clients_list.php` separately gained three cheap tenant-wide per-client booleans (`has_goal_met`/`review_due`/`price_stale`, folded into the existing `needsAttention()` definition) — `goal_drift`/`foundations_gap` are deliberately **excluded** from that bulk path (each needs a second per-client gathering pass that isn't cheap multiplied across a whole tenant, the same asymmetry `goals_met_count` already accepted). Ships **stateless-only**: every alert recomputes fresh on every read, no acknowledge/snooze/`alert_ack` table — a documented, deferred follow-on, not an oversight. Frontend: `AlertsUI.jsx`'s `AlertsCard`/`ClientAlertsCard` (renders nothing when there's nothing to say, same convention as `FoundationsCaveat`), plus two new roster badges on the advisor dashboard.

**Cash-flow module** (docs/10 P0-5) — a unified client cash-flow view: `cash_flow_items` (migration 030, `kind` income|expense, `label`, `amount`, `cadence` monthly|annual, `category`, `is_active`), tenant-scoped via `TenantScopedDb`, per-client on every row. The pure helper `api/lib/CashFlowSummary.php` normalises each line to monthly (annual ÷ 12), sums income/expense/surplus, and — advisor-only — compares surplus to the client's total goal SIPs (the "is the plan fundable from cash flow?" gap). Advisor card + client-facing read-only card (no SIP framing leaked) + a **household roll-up** (`household_cash_flow.php`, sum of members' statements). Balance sheet (portfolio) and cash-flow statement are deliberately separate. Firm/advisor supplies every figure; default empty, no backfill.

**Financial foundations** (docs/10 P1-4) — the four checks a planning standard puts *before* optimising a long-horizon goal: emergency reserve, income-replacement cover, medical cover, and debt costing more than the plan assumes to earn. Built for **both audiences** (advisor card on the client page in planning vocabulary; plain-language card for a self-serve individual, who has no adviser to supply this judgement). The pure helper `api/lib/FinancialFoundations.php` computes everything; only two cover amounts + a dependants count are stored (`client_protection`, migration 034) — expenses/income come from `cash_flow_items` and liquid assets/liabilities from `client_portfolio_items`, deliberately **not re-recorded**, so no figure can drift between two copies. Liabilities gain a nullable `interest_rate`. **Every threshold is a sourced reference point, never a recommendation** (3–6 months of expenses; 10–15× income where dependants exist; ₹5L health-cover floor) — same illustration framing as `lib/strategyPresets.js`; no product, insurer or premium appears anywhere, per P1-4's planning-side-not-distribution scope. Three states are kept strictly distinct and this is the module's whole design: `not_recorded` (unanswered — **never renders as a pass**), `not_applicable` (zero dependants → life cover isn't a gap, it's not needed), and a real shortfall. An untouched portfolio ledger reports the debt check as unrecorded rather than a flattering green "no expensive debt". The readiness score now carries a **caveat** naming what it doesn't cover (it only asks whether the money lasts), rendered only when there is something to say.

**Client-facing** — Meeting Mode (full-screen presentation), printable/shareable client report, DisclosureBanner on every client view, white-label branding, and **client self-service login** (own goals, what-if sliders, read-only portfolio, read-only cash flow, read-only risk band) with all advisor-only reads/writes hidden from a client session.

**Firm governance** — firm roles (`jr_advisor`/`sr_advisor`/`firm_admin`, NULL treated as `sr_advisor`), a **Jr→Sr plan-approval workflow** (`review_status` on `base_plans`, opt-in per tenant, migration 026), approval gates on templates/risk sets, and a **read-only audit log** (`change_log_list.php`, per-goal History card + firm-wide `/activity`).

**Advisor & admin UX** — a **persona-aware dashboard**: the heading and default scope follow the viewer's firm role (jr → "My clients", firm_admin → the whole practice), the attention queue is a surfaced banner carrying the *firm-wide* count (not a hidden checkbox), a book-health bar shows the readiness spread, and the roster does search/sort/scope/**pagination server-side** (`clients_list.php`, 25/page) with per-row advisor assignment. **Client→advisor assignment** (`assigned_advisor_id`, migration 031, `client_assign_advisor.php`) is **attribution only, never an access boundary** — every advisor still reads every client in the tenant; "My clients" is a filter. **Practice analytics** (`/practice`, `firm_analytics.php`, sr_advisor/firm_admin) shows per-advisor load, readiness/risk distribution, the review pipeline and coverage gaps — counts and sums only, never a grade or target. Plus onboarding checklist + spotlight (real advisors), a guided demo tour (public demo only), a 3-step firm-onboarding wizard, firm detail drawer, platform-stats bar, and an in-app **feature guide** (`/guide`). Mobile-responsive throughout (Session 7 audit + tablet/client-role follow-ups); `AppHeader` collapses to a hamburger below `sm`.

**Self-serve individual tier** (sql/033) — an individual can plan for themselves with **no advisor**. Modelled as a **"tenant of one"**: `tenants.kind='personal'`, one user with `role='client'`, `advisory_mode='self_directed'`. Reuses tenant isolation unchanged and adds no new role. Write access is gated on **tenant kind, not role** (`api/lib/SelfService.php`) — an advisor-managed client gains nothing, so the Jr→Sr approval workflow and the audit trail's meaning are untouched. Signup at `/start-free` → guided Q&A at `/start` (`lib/personalPlanner.js`: age/retirement/savings/kids/home → suggested goals; the life answers are **used transiently and never stored**), a retirement **countdown**, plain-language copy throughout (no "decumulation"/"corpus" on screen), and a one-click **individual demo** from the login page. Risk is chosen from sourced, **illustration-framed** bands that set the return assumption — same framing as `lib/strategyPresets.js`, never presented as a recommendation. `initial_net_worth` now accepts **0** ("not started saving yet" is a real state); `PlanMath::readinessScoreForGoal()` returns **null** for a zero corpus rather than the flattering ~89 the raw survival maths would produce.

**Self-serve households — a couple planning together** (sql/035) — two earners in one personal tenant, each with their own login, goals and retirement date. Reuses `households`/`users.household_id` (sql/029) unchanged, because migration 029 already models a household as a **grouping, not a shared pool** — the right shape for a couple (docs/02 §4.1 intact). A partner is invited by email (`household_invite_partner.php`, reusing `password_resets.purpose='invite'` + `/accept-invite`; capped at 5 members as an abuse bound). `household_projection.php` / `household_cash_flow.php` are the only two endpoints opened up, via `verifyHouseholdAccess()` — the same **tenant-kind-not-role** gate as `SelfService.php`, so a *firm's* client still sees nothing, and a personal client is pinned to their own household id. **Both partners read everything; each writes only their own plan** (already enforced by `resolveSelfServiceClientId`, whose own-id check is now load-bearing rather than defensive — see the note in `SelfService.php`). Foundations split by scope: **reserve and debt aggregate across the household** (shared expenses land on whoever entered them, so per-person readings mislead both partners), **cover stays per-person** against each person's own income. `users.display_name` added (nullable, no backfill) since the app had only ever identified people by email.

**Progressive personalisation** (docs/11 Prompt E-2, sql/036) — an opt-in "make this more accurate" queue on the self-serve plan, each question individually skippable and visibly moving a number when answered: **city tier** (7th CPC X/Y/Z, `client_context`) scales only the retirement-YEAR spend inside `PlanMath::retirementTarget()` — never today's recorded cash-flow expenses or the inflation rate — via a **visible, user-overridable multiplier**; an **ongoing medical cost** (rupee figure, never a condition, per §5) adds to that spend; per-child **education cost driver** (government/private/overseas, `client_dependants`, one row per child) surfaces a sourced range against an explicitly-**linked** education goal (`goal_id`, never auto-matched). City tier is **household-shared** (falls back to a partner's answer, same precedent as reserve/debt); medical cost stays **per-person** (same precedent as cover). Sourced figures live in `api/lib/PersonalisationReference.php` — city-tier multipliers stay a pure code derivation from published 7th-CPC HRA percentages (an exact figure, not an estimate — see the reference-cost library bullet below for why that one deliberately isn't cached); education ranges are now **reconciled** with `reference_costs`. Every field defaults to unset, no backfill; `goals_projection.php`'s response carries a `personalisation` block so the goal page states exactly what moved the number, next to the number.

**Sourced reference-cost library** (docs/11 Prompt E-3, sql/037) — `reference_costs`: cited cost ranges (education by driver — government/private/overseas, plus healthcare), each row carrying `low`/`high`, `source_name`, `source_url`, `as_of_date`, and an `is_verified` flag mirroring `market_history`'s unverified-data precedent. Populated by a periodic CLI job (`tools/reference_costs_sync.php`, following `tools/mf_nav_sync.php`'s CLI-only-guard/logic-in-`api/lib/`/failure-leaves-cache-untouched pattern exactly, plus a **prune** step that deletes any cached row the current dataset no longer defines), read via `reference_costs_get.php` (any authenticated advisor/client, not tenant-scoped). **Reconciled with `PersonalisationReference.php`'s education ranges** (this table and that file shipped from two sessions that ran in parallel with mismatched driver granularities — course-specific here vs. generic government/private/overseas there; reconciled by widening this table to the generic enum `client_dependants.cost_driver` actually uses, seeded with `PersonalisationReference`'s own already-live figures so no behavior changed). `PersonalisationReference::educationRangeForDriver()` now reads this cache first (e.g. from `dependants_list.php`) and falls back to its hand-authored constants only while the cache is empty — this table is the real source of truth for education ranges, not a second copy. **City tier stays out of this table on purpose** (an exact HRA-derived formula needs no "sourced range" cache; an earlier draft's city-tier rows used an incompatible baseline and were dropped, per `AskUserQuestion`-confirmed decision, rather than force-reconciled). Healthcare's `ongoing_medical_annual` row is cached and readable but still has no UI consumer (docs/11 §6) — never a point estimate, never a silent fill.

**Platform & access** — self-serve trial signup (always `distribution` mode, `firm_admin` founder) + public "try a live demo" picker; platform settings (MFA enforcement, demo mode, signup toggle) + demo reset (5-min cooldown); magic-link invite activation; a public login-page feature list. Marketing one-pager at `docs/HorizonPlan_One_Pager.html`.

**Individual-flow rebuild + first product analytics** (docs/13 I-1…I-11, sql/040) — the self-serve home screen was inverted: `/goals` for a `personal` tenant now opens with a standing block (`PersonalPlanSummary.jsx` — retirement countdown, readiness score, and **one** next action) then the goals, with the eight data-entry cards moved into a collapsed "Make this plan more accurate" section. It previously rendered all eight *above* the person's goals, so someone finishing onboarding landed on a chore list. **A firm-managed client's ordering is untouched** — the branch is on tenant kind, same gate as `SelfService.php`. The gap-closing levers (`PlanMath::gapClosingLevers()`, built long ago) now surface on that standing block and on a new post-onboarding **proof screen**, both reading the *same* `goals_projection.php` call the goal page uses — `leverLine()` was **exported** from `RetirementTargetCard.jsx` rather than copied, following the `FoundationsInputs.php` precedent, so two surfaces can't state different answers to "what closes my gap". Onboarding no longer dumps the person on the card list; the empty state links to `/start` (it previously described the action with no way to take it, and `/start` was reachable only in the seconds after signup); the risk band starts **unset** rather than pre-filled with 9%; the choice questions are a real `radiogroup` that no longer auto-advances on click; currency inputs are `type="text" inputMode="numeric"` so a stray scroll wheel can't silently change a plan; and the question `min`/`max` ranges — **never actually enforced before**, an age of 200 sailed through — are now checked. `product_events` (sql/040, `api/lib/ProductEvents.php`) is the first telemetry in the codebase: a closed event-name set, a whitelisted non-financial context, and **`tests/test_product_events.php` asserting a rupee figure cannot reach the table** through an unlisted key, a whitelisted integer key, or a numeric string — the privacy rule is enforced by the suite, not by a comment. **Deliberately not built: I-6** (splitting the monthly saving across goals) — investigating it showed the premise was wrong: `goals_create.php` nulls `monthly_sip_amount` for non-retirement goals and `targetGoalFunding()` ignores contributions by design, so the real question is whether target-based goals should have an accumulation model at all. That's a decide-then-build product decision, recorded as an open question in docs/13 §6.

**Individual retention + scenario comparison** (docs/13 I-9/I-10, sql/041) — two follow-ons to the individual-flow rebuild. A **monthly plan digest** (`tools/personal_digest_send.php`, `api/lib/PersonalDigestMailer.php`) emails a self-serve individual a short factual summary, composed from **AlertsEngine's existing facts** rather than a second view of the plan, so an email can never contradict the app; `tests/test_personal_digest.php` asserts no instruction word survives into a body, the same guard the alerts engine holds itself to. **Opt-IN, default OFF** (`users.plan_digest_opt_in`) — docs/13 originally specified opt-out, corrected to match `CLAUDE.md`'s "default new toggles OFF" rule and `PlanReviewMailer`'s own precedent; applying the migration cannot start emailing anybody, a firm's client is never included (their adviser owns the follow-up), and a person with nothing worth reporting is skipped rather than sent "no change this month". **Side-by-side scenario compare** (`ScenarioCompare.jsx`) replaces the accordion's one-at-a-time reading for the specific question scenarios exist to answer; read-only (editing stays in `ScenarioPanel` — an all-editable grid is a spreadsheet, which is what this product replaces), one `goals_projection.php` call per column so no column can disagree with its own panel, and it includes the **adverse-sequence** row naming the year the money runs out rather than a flattering steady-return balance.

**Sourced living-cost anchor** (`api/lib/LivingCostReference.php`, `living_cost_estimate.php`) — a starting point for someone who does not know their own monthly spend, which previously left them with no plan at all (`retirementTarget()` needs an expense figure, and it comes from their own `cash_flow_items`). Sourced from **MOSPI's Household Consumption Expenditure Survey 2023-24** (average MPCE by state and urban/rural), carried as a new `living_cost` category inside the existing `reference_costs` cache. **This shipped believing it needed no migration, and that was wrong (fixed in sql/043).** sql/037 was indeed built for additive *categories*, but it declared `unit VARCHAR(20)` and the living-cost unit (`inr_monthly_per_capita`) is 22 characters — so MySQL rejected all 15 rows with `SQLSTATE[22001] Data too long`, `syncReferenceCosts()` fataled part-way through, and the feature was live but unable to store its own data. The stale unit whitelist in `tests/test_reference_costs_db.php` had been masking it (the pure-dataset assertion exited before the DB write was reached); both are corrected, and the assertion now guards the invariant that actually matters — *absolute rupee units only, never a multiplier* — rather than an enumerated list that goes stale. `sql/manual/reference_costs_seed.sql` repeats the widening ALTER at its top so a single paste still works. Folded into `referenceCostDataset()` rather than given its own sync tool on purpose: `syncReferenceCosts()`'s prune selects *every* row in the table and deletes anything its own dataset doesn't define, so a second tool's rows would be silently removed on the next run. **Numbeo was asked for and declined** — its terms prohibit scraping, and its commercial licence forbids disseminating the data through a public-facing product without separate consent; docs/11 §3 already ruled out crowd-sourced cost-of-living sites and now records the specific finding. **The figure is never pre-filled into the person's expense field** — MPCE is an average across *all* households and this product's users spend well above it, so an uncritical anchor would understate a retirement target, the one error this app must not make quietly. It renders beside their own input, scaled per-capita → household, carrying the API's own caveat verbatim, and states plainly when it has fallen back to the all-India figure rather than their state's. The state table is **deliberately partial** (only states whose published figure is actually known); the rest fall back to all-India, flagged. Every row seeds `is_verified=0`, same precedent as `market_history`/`tax_reference`.

**Individual dashboard: identity, trend and the moving answer** (sql/042) — three additions to the self-serve standing block, decided against both the practitioner view and what individuals actually ask for. (1) An **identity + assumption strip** on `PersonalPlanSummary.jsx` — name, current age, retirement age. Not decoration: `current_age`/`retirement_age` are the two most load-bearing inputs in the plan (they set the horizon every other number is computed over) and were previously visible only by opening a goal, so a wrong age silently invalidated the whole projection with nothing on screen to catch it. `session.php` now returns `display_name`/`email`; `displayNameFor()` in `AuthContext.jsx` holds the one fallback chain (display_name → email local part → render no greeting at all), since sql/035 left `display_name` nullable and un-backfilled. (2) **`NetWorthTrend.jsx`** — the missing consumer for `client_net_worth_snapshots`, which had a table, a monthly cron, an endpoint (`client_progress_read.php`) and an API method and *no UI at all*; the series had been accumulating unseen. (3) A **readiness delta** — `goal_snapshots.readiness_score` (sql/042, nullable, no backfill) records the score *as the plan stood* on each date, so the dashboard can say "62 in March, 71 now"; `goal_progress_read.php` gained a `readiness_change` block computed over **scored points only** (a NULL row is a target-based goal, a zero corpus, or a pre-migration row — never a zero), null below two of them, mirroring `client_progress_read.php`'s existing refusal to report a change from one reading. **Both deltas are framed "since <month>", never month-over-month, and no monthly figure is computed anywhere** — a monthly scoreboard on a multi-decade plan trains exactly the frequent-evaluation habit (Benartzi & Thaler, myopic loss aversion) that leaves long-horizon investors worse off; the ban is stated in each file's header so it isn't quietly reversed. `NetWorthTrend` renders nothing below **three** points (two joined dots read as a trend when they are just the only two facts held). Both are **personal-tenant only**, the same `tenant.kind` branch as docs/13 I-1 — a firm-managed client's progress narrative belongs to their adviser, who already has this series on the client page.

**Alert voice — second person for the person themselves** — found by the browser check on the dashboard above, not by a test: `AlertsEngine` built every message as `"{$clientLabel}'s …"`, so a self-serve individual read *"Priya Raman's emergency reserve has not been recorded yet"* about herself, and the **monthly digest email inherited it verbatim** (`composeDigestBody()` embeds `factual_message` unchanged). Fixed at the engine, not per-surface: `alertPossessive($clientLabel, $isSelf)` returns `"Priya Raman's"` or `"Your"` — a **possessive**, because "Your" cannot be produced by appending `'s` to a label, so a label alone could never express the second-person case. `AlertsInputs` sets `is_self` from **tenant kind** (`tenantIsPersonal()`), the same gate `SelfService.php` uses everywhere — a firm's client role says nothing about who is reading, but a "tenant of one" is always reading about themselves. The parameter defaults to the advisor wording, so any caller that hasn't opted in can't accidentally address a stranger as "you". `TenantScopedDb::tenantId()` added as a **read-only** accessor (no setter, ever — the isolation guarantee rests on the tenant being fixed at construction). Tests assert both forms, that the person's own name never appears in an alert addressed to them, and that perspective changes **wording only** — same alerts, same types, same severities; both verified over real HTTP against a firm tenant and a personal one.

## Deploy
**Automated (preferred):** `.github/workflows/deploy.yml` builds the React app on every push to `main` (touching `frontend/`, `api/`, or the workflow) and publishes a `public_html`-shaped tree — compiled `dist/` at the root plus `api/` under `/api` — to a dedicated **`deploy` branch**, building on top of that branch's history (never force-pushed) so Hostinger's `git pull` always fast-forwards. Hostinger's native Git deployment (hPanel → Advanced → GIT, branch `deploy`, directory `public_html`) pulls it automatically. **`api/db_config.php` is now a tracked, secret-free loader, not a git-ignored credentials file** — found in production that Hostinger's Auto-Deployment resets/cleans the working tree on every push (not a plain pull), which was silently wiping the old untracked credentials file on every deploy regardless of permissions. The loader points at an absolute path outside `public_html`, which the reset can't reach; every `api/*.php`/`tools/*.php` call site needed no changes. **Full setup + gotchas in `DEPLOY.md`'s "Database credentials" section**, reasoning in `api/db_config.php`'s own header. Note: the workflow only fires from `main`, so it activates after this branch is merged, not on the feature branch itself.

**Manual fallback:** build locally (`cd frontend && npm run build`), then upload the `dist/` output into `public_html` via Hostinger's File Manager alongside `public_html/api`. Watch two things this replaces: `.htaccess` is a hidden dotfile inside `dist/` that file managers drop, and every `dist/` file (including `assets/`) must land at the `public_html` root together or the absolute `/assets/…` paths 404.

SQL migrations in `/sql` are **not** run automatically under either path — run new migrations manually via hPanel's database tool after each deploy that includes one.
