# HorizonPlan

B2B2C retirement planning platform for Indian MFDs/IFAs and SEBI-RIA firms. Full context lives in `/docs/` — read the relevant file before starting work on that area, don't assume this file alone is enough.

## Stack
PHP (no framework) + PDO + MySQL, hosted on Hostinger Premium. React SPA (Tailwind, shadcn/ui), pre-compiled — Hostinger serves static files, it does not run a Node build step, so the frontend must be built (`npm run build`) before every deploy. A `.github/workflows/deploy.yml` pipeline now automates this by publishing the compiled output to a `deploy` branch — see "Deploy" below and `DEPLOY.md`.

## Non-negotiable rules (always apply, every session)
1. **Tenant isolation:** every query on tenant-scoped data goes through `api/lib/TenantScopedDb.php`. Never write a raw `WHERE tenant_id = :tenant_id` inline in an endpoint file — if the helper doesn't exist yet, build it first (see `docs/02`, Section 3.1).
2. **`advisory_mode` on tenants is Super Admin-only**, enforced server-side, never a self-serve toggle. See `docs/02` Section 3.6.
3. **Distribution-mode disclosure copy** renders on every client-facing plan view, and directly adjacent to the withdrawal-rate slider and projection chart specifically.
4. Every mutation to `base_plans` / `sub_scenarios` writes to `change_log`.
5. No credentials in the repo. `db_config.php` stays out of git.
6. Don't build anything from `docs/04`'s "explicitly out of scope" lists without checking the phase validation gate first.

Phase 6 is built: the Live Timeline Slider (`components/LiveTimelineSlider.jsx`), Reset Trigger Control, and the withdrawal-rate slider + corpus-multiple readout + sequence-risk chart (`components/ScenarioPanel.jsx`, `SequenceRiskChart.jsx`, using `recharts`) — wired to `subscenarios_update.php`, `subscenarios_reset.php`, and `goals_projection.php` as they actually behave, not as the Phase 6 prompt's prose implied:
- `goals_projection.php` only accepts a persisted `sub_scenario_id` (or none, for the parent goal's own values) — it does not take ad hoc rate parameters. So the chart is **not** literally redrawn on every drag frame; it redraws once per committed save (same debounce as the write), which is what "redrawn whenever either slider moves (debounced the same way)" resolves to given the real endpoint shape. The corpus-multiple readout, by contrast, genuinely is live client-side feedback per Section 4.2, computed with the same formula as `PlanMath::corpusMultiple()`.
- "Debounced on release" is implemented as an actual release event (`onMouseUp`/`onTouchEnd`/`onKeyUp`), not a timer — this is stricter than a debounce, not looser: exactly one write per drag, and one per discrete keyboard adjustment.
- Both sliders write through the *same* `is_overridden` flag per `subscenarios_update.php` (docs/02 4.2 — not a bug, documented shared-flag behavior), so touching either one freezes the whole sub-scenario from cascade updates on all three fields.
Phase 7 (heavy computation) was evaluated and explicitly skipped: `PlanMath.php` is pure in-memory arithmetic (its own docblock: "no DB access"), O(horizon_years) with horizon now capped at 1–100 (see Phase 8 below — it was previously unbounded), sub-millisecond per request, nowhere near Hostinger's 30s ceiling. Building the `jobs` table / cron worker / polling infra here would be speculative, against Phase 7's own instruction not to build it without a demonstrated need. Revisit only if a future phase adds genuinely heavy computation (e.g. real Monte Carlo simulation) — don't assume this skip still holds for a different computation without re-checking.

## Security status
Phase 8 audit gaps now resolved — both MFA and CSRF double-submit tokens are implemented. **One pre-launch gap remains: MFA enrollment is not yet mandatory** — users without `mfa_secret` set still get a full session on password alone. Closing this requires a deliberate decision (block non-enrolled users at login, or build an admin-forced enrollment flow) before going live with real client accounts.

### Audit findings, file-by-file

**MFA** — **Implemented** (RFC 6238 TOTP, no external dependency — `api/lib/Totp.php` is pure PHP). Login forks on `users.mfa_secret`: enrolled users get a 202 + short-lived `hp_mfa_pending` cookie, then submit OTP to `mfa_verify.php` for a full session. Enrollment is a two-step flow (`mfa_enroll.php` → `mfa_enroll_confirm.php`) available to any authenticated user. Pending tokens live in `mfa_pending` (migration 008), are single-use, expire in 10 min, carry the TOTP secret server-side in `payload` so it never lives in JS. **Remaining gap: enrollment is not mandatory** — unenrolled users still get a full session on password alone. Don't go live until this is explicitly decided and handled.

**Credentials in repo** — Checked `db_config.example.php` (placeholder values only, correctly named `.example`), confirmed `api/db_config.php` is git-ignored and not present in any tracked commit (`git log --all --full-history -- api/db_config.php` returns nothing), confirmed `.gitignore` covers it. **Clean.**

**Endpoints routing through the two shared helpers** — Checked all 11 endpoint files (`login.php`, `logout.php`, `session.php`, `goals_{list,create,read,update,projection}.php`, `subscenarios_{list,create,update,reset}.php`). All require `security_gatekeeper.php`; all except `login.php`/`logout.php`/`session.php` (which legitimately precede any session) also require `TenantScopedDb.php`. **One real violation found and fixed this pass:** `TenantScopedDb`'s own docblock claimed to cover `base_plans, sub_scenarios, users, change_log`, but `ALLOWED_TABLES` only actually listed three of those four — `users` was missing. That gap forced `goals_create.php`'s client-tenant-ownership check to drop to a raw `$db->prepare()` call instead of the helper. The raw query itself was still correctly parameterized and tenant-filtered — not a cross-tenant leak as found — but it was a structural exception to "no exceptions to the helper pattern." Fixed: added `'users'` to `ALLOWED_TABLES`, refactored `goals_create.php` to `$scopedDb->select('users', ...)`. Also grepped for any other inline `WHERE tenant_id = :` outside `lib/` — zero other matches. **Now clean**, but checked from source, not a live DB — worth an integration-test pass against real endpoints too, not just static grep.

**`change_log` written on every mutation** — Checked every mutation path directly (not from memory): `goals_create.php` (line 72), `goals_update.php` (both the direct field edits, lines 68-77, and every cascaded child row, lines 112-121 — the cascade update and its audit rows are written in the same block, so they can't drift apart), `subscenarios_create.php` (line 55), `subscenarios_update.php` (both the field changes and the `is_overridden` flag flip), and `subscenarios_reset.php` (all three reset fields plus the flag flip back to 0). **Clean — verified by reading each file, not assumed.** Correction: an earlier pass of this audit claimed `goals_create.php` was missing its `logChange()` call. That was wrong — I stated it without opening the file first. Re-checked directly (line 72 calls `logChange('base_plan', $goalId, 'created', null, json_encode($data), ...)`) and the claim doesn't hold. Leaving this correction in the record rather than quietly fixing it, since a false "gap found" is exactly the kind of claim this audit exists to prevent.

**CSRF protection** — **Implemented** (double-submit cookie pattern). `issueSession()` and `session.php` now set a non-httpOnly `hp_csrf` cookie alongside the httpOnly session cookie. `verifyAccess()` and `verifyAccessAny()` call `verifyCsrfToken()` on every non-GET request, checking `hash_equals($cookie, $header)` where the header is `X-CSRF-Token` sent by the frontend's fetch wrapper (`api.js`, reads the cookie and attaches it). `destroySession()` clears both cookies. Login flow endpoints (`login.php`, `mfa_verify.php`) are intentionally exempt — the CSRF cookie doesn't exist yet at that point, and the pending-token + `httpOnly`/`Strict` chain already protects those requests; this decision is documented inline in `mfa_verify.php`.

**XSS** — Checked `frontend/src` for `dangerouslySetInnerHTML`, raw `innerHTML` assignment, and `eval` — none found. User-generated strings that actually render (goal labels, scenario data) go through React's default JSX escaping, not a manual `innerHTML` path. **Clean.**

**`projection_horizon_years` bound** — Not on the original Phase 8 checklist, found while reasoning through the Phase 7 skip decision: `sql/004_base_plans.sql` declares it `INT UNSIGNED NOT NULL DEFAULT 30` with no `CHECK` constraint, and neither `goals_create.php` nor `goals_update.php` validated it — zero, negative (blocked by `UNSIGNED` at the DB layer, but PHP would still have tried), or absurdly large values were all accepted before reaching the DB. Not a security issue (the projection loop is cheap regardless of horizon, confirmed under Phase 7 above) but a real data-sanity gap. **Fixed:** added a 1–100 range check in both `goals_create.php` and `goals_update.php`, returning 400 outside that range.

**Rate limiting** — Not part of the Phase 8 checklist above, but noticed in passing and independently re-verified this pass (`grep -n "RateLimit" api/*.php api/lib/*.php`): `login.php`/`security_gatekeeper.php` rate-limit login attempts (`checkLoginRateLimit`), but no other endpoint (`goals_*`, `subscenarios_*`) has any rate limiting. Worth a decision on whether that's intentional for MVP scale or a gap to log for later — not fixed here, since it wasn't asked for.

**Also found, flagged, deliberately not fixed:** `goals_update.php`'s partial-update loop has no type/range validation at all for the rest of `$updatableFields` (`initial_net_worth`, `inflation_rate`, `target_amount`, `target_date`, `withdrawal_rate`, `drawdown_return_rate`) — only `projection_horizon_years` now has a check. Widening this to every field is a real gap worth its own dedicated pass, not something to absorb quietly into a security audit that was already running long.

**Summary:** All 7 original checked items are now either clean or resolved. MFA (TOTP) and CSRF (double-submit) are both implemented as of the post-Phase-8 hardening session. The one still-open pre-launch item is mandatory MFA enrollment — unenrolled users still get a full session on password alone. The other known gap (per-field input validation on `goals_update.php` for fields other than `projection_horizon_years`) remains flagged and unresolved, out of scope for both audit sessions.

**Password reset (self-service, added post-Phase-8)** — Until this addition, the only account-recovery path was the CLI-only `tools/set_password.php`/`tools/bootstrap_admin.php` (SSH access required) — unworkable for real advisor/client tenants who can't SSH into the server. `password_reset_request.php` / `password_reset_confirm.php` add an email-link flow: `password_resets` (migration 009) stores only a SHA-256 hash of the token (never the raw value — a stricter property than `mfa_pending`'s stored-raw-token, since a leaked reset token alone is a full account takeover, not a second factor); tokens are single-use (`used_at`) and expire in 30 minutes; the request endpoint's response is byte-identical whether or not the email exists (anti-enumeration) and is rate-limited to one live token per user per 2 minutes; redeeming a token invalidates every other outstanding token for that user and clears all of that user's `active_sessions`. Both endpoints are intentionally unauthenticated/CSRF-exempt, same reasoning as `login.php`/`mfa_verify.php` (no session exists yet to protect). Email is sent via PHP's native `mail()` (`api/lib/Mailer.php`) — no SMTP/composer dependency added speculatively; swap to Hostinger SMTP only if deliverability actually proves insufficient. Verified end-to-end against a real MySQL instance (not just static review): request/cooldown/anti-enumeration, confirm/expiry/single-use/reuse-rejection, and the full loop (new password logs in, old password is rejected) all behave as designed. `tests/test_password_reset_db.php` covers this in CI.

## Deploy
**Automated (preferred):** `.github/workflows/deploy.yml` builds the React app on every push to `main` (touching `frontend/`, `api/`, or the workflow) and publishes a `public_html`-shaped tree — compiled `dist/` at the root plus `api/` under `/api` — to a dedicated **`deploy` branch**, building on top of that branch's history (never force-pushed) so Hostinger's `git pull` always fast-forwards. Hostinger's native Git deployment (hPanel → Advanced → GIT, branch `deploy`, directory `public_html`) pulls it automatically. `api/db_config.php` is stripped in CI and lives only on the server, so pulls never touch it. **Full setup + gotchas in `DEPLOY.md`.** Note: the workflow only fires from `main`, so it activates after this branch is merged, not on the feature branch itself.

**Manual fallback:** build locally (`cd frontend && npm run build`), then upload the `dist/` output into `public_html` via Hostinger's File Manager alongside `public_html/api`. Watch two things this replaces: `.htaccess` is a hidden dotfile inside `dist/` that file managers drop, and every `dist/` file (including `assets/`) must land at the `public_html` root together or the absolute `/assets/…` paths 404.

SQL migrations in `/sql` are **not** run automatically under either path — run new migrations manually via hPanel's database tool after each deploy that includes one.
